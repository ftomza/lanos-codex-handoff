# Запись поездки для топливного компьютера

Грабер — режим `--record` нашей Go-утилиты `obdprobe`. Он сохраняет реальные
ответы для последующего анализа, но пока **не рассчитывает расход топлива**.
Новых зависимостей нет; используются существующие Go BLE/SPP и ELM parser.
BLE baseline и supported scan проверены физически. Владелец также записал
60s на стоянке и 14 мин 36 с поездки 2026-10-28. Основные PID опрашивались
примерно раз в 1.02s, без gap/recovery событий. Найдены непроверенный IAT
(−40°C → постоянные +20°C) и failed при завершении после выключения двигателя
и Ctrl+C; точная ошибка cleanup отсутствует в summary. Подробности в
capabilities.md. Это не проверка длительной надёжности или восстановления.

## Перед первой поездкой

Из корня проекта на MacBook с Go 1.27+, CGO и Xcode tools:

```sh
make build-obdprobe
```

Оставьте `bin/obdprobe-ble` рядом с `bin/obdprobe`. Подключите Vgate, закройте
другие OBD-клиенты. Сначала на припаркованной машине с включённым зажиганием
выполните короткую проверку записи:

```sh
./bin/obdprobe --transport=ble --record --duration=1m --retries=0
```

Начальный поиск протокола может занимать до 30 секунд. Дождитесь сообщения
`Recording active`, проверьте список `missing fuel-model inputs` и счётчики
ошибок. Список содержит отсутствующие или недоступные после начального scan
RPM `0C`, MAP `0B`, скорость `0D`, IAT `0F`; подробные support/status есть в файле.
Пустой список не гарантирует, что эти параметры останутся доступны всю поездку.
Короткая проверка не доказывает устойчивость связи во время движения.

## Запуск записи поездки

На стоянке, перед выездом, из корня проекта:

```sh
caffeinate -i ./bin/obdprobe --transport=ble --record
```

По умолчанию используется `IOS-Vlink`, запись ограничена **4 часами**. Путь
файла утилита напечатает сразу: `diagnostics/trip-<UTC-время>-<суффикс>.jsonl`.
Каждый запуск создаёт новый файл с правами 0600; существующие не перезаписываются.
Если путь задаётся через `--output`, родительский каталог должен существовать.

`caffeinate -i` предотвращает сон по бездействию, пока работает команда. Он не
гарантирует работу при закрытой крышке. Оставьте MacBook открытым, закреплённым,
с питанием и вентиляцией; не закрывайте Terminal. Запускайте и проверяйте запись
только на стоянке, в движении ничего не нажимайте и не следите за терминалом.

Для другой длительности или имени файла:

```sh
./bin/obdprobe --transport=ble --record --duration=6h \
  --output=diagnostics/my-trip-001.jsonl
```

Допускается положительная длительность до 24h. После парковки нажмите **Ctrl+C**
и дождитесь `Recording ended`. Длительность и Ctrl+C предназначены для штатного
завершения. В первой поездке после engine-off/Ctrl+C зафиксирован failed;
при повторении сохраните также финальную ошибку из Terminal для разбора cleanup.
Не удаляйте JSONL: уже записанные строки могут оставаться пригодными для анализа.
Ошибка транспорта, диска, размера файла или исчерпание повторов дают ненулевой
код выхода. Сообщение об окончании содержит причину, счётчики и путь файла.
Старые параметры режима разового отчёта работают как прежде. `--record` нельзя
совмещать с `--json`, `--scan-supported` или `--list-ports`.

## Что записывается

Сначала выполняется полный capability-gated scan. Затем в каждом основном круге
читаются заявленные **RPM → MAP → скорость**. Целевой интервал начала кругов —
1s; медленный ответ увеличивает его, очередь догоняющих запросов не создаётся.

После круга читается не более одного просроченного вспомогательного параметра:

| Параметры | Целевой интервал для каждого |
| --- | --- |
| Дроссель, топливный статус Mode 01 PID 03 | 3s |
| STFT, температура впуска | 5s |
| ОЖ, O2 №1/№2, нагрузка, опережение зажигания | 10s |
| LTFT | 30s |
| MIL/readiness, питание адаптера ATRV | 60s |

Параметр с самым ранним сроком опрашивается первым. Интервалы — ориентиры
расписания, фактические могут быть больше из-за ограничений K-Line/BLE и записи
на диск. Время и задержка каждого запроса сохраняются для анализа. Параметры
читаются последовательно и не образуют одновременного снимка двигателя.

PID 03/13/21/22 из начального scan сохраняются как `raw_only`, где ещё нет
семантического декодера. Для дальнейшего разбора этого достаточно. MAF, уровень
топлива, ECU voltage и fuel rate не запрашиваются в обход bitmap. Mode 03 читает
сохранённые DTC в начале сегмента; pending/permanent/VIN не запрашиваются.
Никакой очистки ошибок, ECU-записи или калибровки адаптера нет.

## Обрывы и сохранность

По умолчанию доступны **два дополнительных восстановления за всю запись**,
а не за каждый обрыв. После timeout/reopen сначала ожидается prompt; затем
повторяются инициализация и discovery. Если prompt не приходит или бюджет
исчерпан, запись останавливается с сохранением частичного файла. Не пытайтесь
чинить соединение во время движения. После парковки можно начать новый файл.

Ошибки и пропуски записываются явно; `NO DATA` не становится нулём, предыдущие
значения не подставляются в новый ответ. Нулевые RPM сами по себе не завершают
запись и не доказывают отключение подачи топлива.

Каждое событие записывается и синхронизируется с диском до следующего запроса.
Это может снижать частоту опроса; измеренная частота будет видна по меткам.
Лимит файла — **256 MiB**, часть зарезервирована для итога. Ошибка записи/sync
останавливает дальнейшие запросы. История поездки не накапливается в RAM.
При внезапном выключении питания последняя строка всё равно может оказаться
неполной; сохраните файл целиком. Ранее завершённые строки читаются независимо.
Отсутствие `recording_end` означает незавершённый журнал, а не нулевой расход.

Файлы локальные и исключены из Git. Узнаваемые VIN по умолчанию скрываются,
в том числе в строках ошибок. Записи не загружаются и не публикуются автоматически.

## Что сохранить вместе с поездкой

Обычной поездки достаточно: естественные прогрев, холостой ход, городское и
равномерное движение. Специальные разгоны, обороты или манёвры не нужны.
Отдельно запишите:

- Дату, примерные начало/конец и показания одометра до/после.
- Вид топлива: бензин или газ; при переключении — примерное время. Бензиновая
  модель не должна молча применяться к поездке на газе.
- Необычные условия: пробки, кондиционер, большой груз, остановки записи.
- Для калибровки: две заправки до полного, одометр на обеих и сколько литров
  долито на второй; все промежуточные заправки и записи поездок между ними.

Логи помогут подобрать модель и проверить покрытие, но сами по себе не дают
истинного расхода или точного коэффициента наполнения. Для оценки литров нужны
независимые данные заправок. Прогрев, обогащение и торможение двигателем остаются
источниками ошибки. O2/коррекции не превращают эту оценку в измеренный fuel flow.
Не интегрируйте разрывы или слишком старые значения как непрерывные показания.
Если записи покрывают только часть интервала заправок, это нужно учитывать при
сопоставлении, а не приписывать всё заправленное топливо записанным поездкам.

## Формат для последующего анализа

JSONL: одна самостоятельная JSON-строка на событие. Верхние поля:
`schema_version=1`, `sequence`, `type`, `timestamp` (host UTC), `elapsed_ns`
(монотонное время от начала), `segment`, `data`. Часовой пояс отображения
Europe/Moscow указан в metadata; время захвата ЭБУ не выдумывается.

Типы: `recording_start`, `segment_start`, `command`, `capabilities`, `gap`,
`recovery`, `segment_end`, `recording_end`. В command находятся raw/status/error,
wall-clock start/end, монотонные `started_elapsed_ns`/`completed_elapsed_ns`,
`latency_ns` и `result`, когда команда относится к данным. `result.status`
различает available/raw_only/capability/temporarily_unavailable/invalid_response.
JSON null/отсутствующее числовое поле не означает ноль.

Итог содержит счётчики, длительность и `polling_ns`/`unobserved_ns`. Это время
работы цикла опроса и остальное время, включая запуск/восстановление; оно не
гарантирует полноту или пригодность всех входов для топливного расчёта.
При разборе нужны фактические интервалы каждого PID и события gap/segment.
