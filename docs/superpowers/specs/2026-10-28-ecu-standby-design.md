# LIVE dashboard: ожидание ЭБУ и возврат после выключения зажигания

Дата: 2026-10-28. Ветка: `fix/ecu-standby`, от main `87f324e`.
Статус: проект решения, ожидает одобрения владельца; код не изменён.

## Проблема и установленная причина

Владелец сообщил об успешном запуске LIVE с топливным компьютером после
слияния PR #3. При подключённом адаптере и выключенном зажигании, а также
после выключения зажигания приборка предлагает перезапуск.

`internal/probe/record.go` ограничивает Stream общим числом попыток, даже
если HTTP-сервер продолжает работать. `internal/live/source.go` после
завершения Stream публикует требование перезапуска. Дополнительно
`internal/live/events.go` считает capabilities и последующие команды
подтверждением связи с ЭБУ, хотя discovery может вернуть недоступную
битовую карту, а AT-команды подтверждают только связь с адаптером.
Завершённые ответы NO DATA/UNABLE TO CONNECT не запускают восстановление:
readPID помечает отдельное значение недоступным и возвращает nil.

Положение ключа напрямую не измеряется. Отсутствие ответа ЭБУ не доказывает,
что зажигание выключено. RPM=0 при отвечающем ЭБУ — нормальное показание.

## Варианты

1. **Рекомендуется:** режим ожидания в непрерывном LIVE с редкими проверками
   ЭБУ и отдельным восстановлением транспорта. Работает при запуске без
   зажигания и при последующем выключении, включая потерю BLE.
2. Только заменить текст и добавить ручную кнопку повтора. Проще, но
   требует действий владельца после каждого выключения зажигания.
3. Ждать только при доступном адаптере, оставив потерю BLE терминальной.
   Меньше изменений, но известные разрывы Bluetooth при смене зажигания
   всё ещё потребуют перезапуска.

## Поведение

- Пока свежий ответ адаптера подтверждает соединение, но ЭБУ не отвечает:
  «Адаптер подключён. ЭБУ не отвечает — возможно, зажигание выключено.
  Ожидаем…».
- Если нет подтверждённой связи с адаптером: «Нет связи с адаптером.
  Ожидаем подключения…». Не указывать зажигание как установленную причину.
- HTTP/SSE остаются доступны, источник всегда LIVE. В ожидании `health`
  равен `connecting`; используются существующие message и статусы сигналов,
  без нового публичного значения health. Текст объясняет причину ожидания.
- При входе в ожидание очистить текущие значения и их глобальную свежесть,
  включая мгновенный расход. Не подставлять нули. Сохранить накопленные
  литры/километры, время сброса и калибровку; показать неполное покрытие.
- До возврата к connected повторить discovery и начать новое поколение
  измерений. Только корректный свежий ответ Mode 01 подтверждает связь с ЭБУ;
  AT-ответы и пустой capabilities не переводят источник в connected.
- Ошибка одного PID не означает выключенное зажигание: остальные доступные
  сигналы продолжают обновляться и независимо истекать.

## Опрос и восстановление

Изменить только непрерывный Runner.Stream и LIVE Source. Однократный Run
и ограниченный по времени Record сохраняют прежние попытки, расписание,
формат отчётов и правила завершения. Симулятор не меняется.

При первом discovery без доступного 0100 перейти в ожидание сразу. После
работающей сессии перейти в ожидание после трёх последовательных полных
раундов без корректного ответа от всех опрашиваемых поддерживаемых основных
PID; успешный ответ сбрасывает счётчик. Для набора без основных PID проверять
доступность через 0100 раз в 10 секунд вместо ложного connected от ATRV.
Обычные TTL продолжают скрывать старые значения до порога перехода.

В ожидании выдерживать отменяемую паузу 10 секунд между проверками. На
синхронизированном соединении проверять ATI и 0100. Если ЭБУ появился,
выполнить обычный discovery и возобновить расписание; не выполнять полный
scan, DTC и опрос всех PID на каждом отрицательном ответе ожидания.
Пауза отсчитывается после завершения предыдущей проверки; команды имеют
существующие таймауты, поэтому фактический интервал может быть больше 10с.

При потере транспорта использовать ограниченные серии восстановления:
`1 + --retries` попыток с существующим backoff, затем 10 секунд ожидания
перед новой серией. Для LIVE `--retries=0` означает одну попытку в серии,
а не окончательное прекращение ожидания. Это явное изменение ранее
утверждённого общего бюджета M4: ограничена серия, а ожидание продолжается
до отмены процесса. Обновить help/README/NEXT_CONNECTION соответственно.
В памяти хранится только актуальное состояние и ограниченные счётчики.

После таймаута, включая повторное открытие транспорта с незавершённой
командой, сначала прочитать ожидающий prompt `>` через существующий Recover.
До синхронизации не отправлять ATI, 0100, инициализацию или ATZ. Если prompt
не приходит, оставаться в состоянии восстановления; не обходить защиту
сбросом/слепой очисткой буфера. Отмена прерывает чтение/паузу/открытие.

Повторять только распознанные временные транспортные ошибки и отсутствие
ответа ЭБУ. Не прятать ошибки конфигурации/прав доступа, несовместимую
инициализацию, неизвестные нетранспортные ошибки, ошибки sink и cleanup:
они остаются явными терминальными ошибками с причиной. Обновление страницы
не должно создавать второй worker или отдельную BLE-сессию.

## Проверки и границы

Регрессионные тесты до реализации: запуск без ответа ЭБУ; три неуспешных
раунда после нормальной работы; возврат ответов без перезапуска; RPM=0 с
зажиганием; отдельный недоступный PID; отсутствие основных PID; потеря
адаптера и восстановление при retries=0; AT-ответы не создают connected;
ожидание позднего prompt до записи; отмена во всех ожиданиях; настоящие
терминальные ошибки и cleanup не скрыты. Проверить неизменность Run/Record.

Проверить Source/HTTP/SSE и браузер: ожидание сохраняет LIVE и ясный текст,
не показывает старые числа, два клиента используют один источник. Проверить
топливный компьютер: итоги сохраняются, мгновенные значения недоступны,
поколение не позволяет интегрировать топливо/расстояние через разрыв даже
если промежуточное событие ожидания пропущено медленным потребителем.

Проверки реализации: `go test ./... -count=1`, `go test -race ./...`,
`make lint`, `make test-web`, `make build-dashboard`, `make build-obdprobe`,
`git diff --check`. Go 1.27 и зависимости остаются прежними.

Сейчас подключений к автомобилю не выполнять. После offline-проверок нужна
отдельно согласованная физическая проверка на припаркованной машине:
запуск с адаптером без зажигания → включение → нормальные данные → выключение
→ ожидание → повторное включение → возврат данных и сохранение итогов.
Отдельно проверить пропажу BLE. Фактические задержки и поведение Vgate во
сне пока неизвестны; автоматическое пробуждение адаптера не гарантируется.
Новых ECU-команд, записи/очистки, ADAS, уровня бака и калибровки топлива
в этой задаче нет.
