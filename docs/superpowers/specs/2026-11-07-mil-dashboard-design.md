# M3.3.6 — Экран диагностики Dashboard

## Зачем и что входит

Владелец продолжает M3.3 после готового offline-анализатора M3.3.5. Нужна
понятная страница браузера: текущее состояние Check Engine, последние ответы
DTC и сохранённые события с контекстом и результатами анализа. Ветка
`feat/mil-dashboard` создана от `feat/mil-analysis` (1cb2909).

Функциональные требования уже заданы разделом 8 M3.3 в PLAN. Сохраняются один
ELM-сеанс, существующие частота/очередь команд, TTL, Fuel Computer, зависимости
и Go. Страница не отправляет диагностические команды в автомобиль и не имеет
очистки DTC. M3.3.7 и новое подключение к машине не входят в этот этап.

## Подходы

Выбор исполнителя: отдельная `/diagnostics.html` в существующем оформлении,
живые данные из SSE и сохранённые отчёты из `milanalysis` через read-only HTTP.
Это повторяет устройство `/analytics.html` и оставляет приборы легко читаемыми.

Альтернатива — разместить всю диагностику на главной — перегружает экран
1280×800. Отдельное приложение или subprocess CLI на каждый запрос дублировали
бы уже готовые сервер, анализатор и формат отчёта. Они не нужны для M3.3.6.

Новый UI без фронтенд-библиотек, в существующих HTML/CSS/ES modules. Подробности
оформления и разбиения кода исполнитель выбирает в рамках текущего стиля.

Главная и аналитика получают ссылку «Диагностика». На странице диагностики есть

и узкого экрана; детали — в раскрываемых блоках. `role=status/alert`, подписи,
keyboard navigation и состояние загрузки обязательны. Цвет дополняет текст.

## Текущий MIL и последние ответы

Страница использует существующий `Feed` и `/events`, без отдельного OBD-клиента.
Модель представления проверяет связь, здоровье источника, status и отдельные
captured/received/TTL MIL. В браузере к server_time добавляется монотонное время
с момента получения; часы планшета не считаются синхронными с сервером.
Watchdog обновляет свежесть даже при отсутствии новых SSE-сообщений.

Свежий MIL ON/OFF показывается только при доступном источнике и валидных
данных. Просрочка, NO DATA, потеря SSE или неизвестные данные дают UNKNOWN,
не OFF. Число DTC — из свежего 0101, иначе прочерк. До первого успешного ответа
время последнего успеха неизвестно; браузер может удерживать время успешного
ответа, увиденного при этом открытии страницы, с явной такой подписью.

Stored/pending/permanent — последние сохранённые в snapshot ответы, с их
собственными timestamp/status; они не объявляются одновременными свежему MIL.
Смена поколения соединения разрывает доверие к текущему чтению; прежние ответы
можно показывать только с маркировкой исторических/последних известных.
Код и его описание не означают установления неисправной детали.

Если свежий MIL ON не объяснён доступными кодами, показать:
«Check Engine включён. Причина не определена стандартными диагностическими режимами».
Нельзя писать «Ошибок нет». Успешный пустой список, отсутствие запроса,
unsupported, временная недоступность и invalid_response имеют разные подписи.
Не согласованные по структуре status/codes не превращаются в пустой успех.

В режиме SIM без MIL явно написано, что MIL симулятором не предоставляется.
Текущий источник SIM и архив LIVE показываются независимо; один не заменяет
другой. Ошибка чтения истории не скрывает текущие данные или Fuel Computer.

## Доступ к архиву и HTTP

Добавить `--mil-history-dir` для чтения архива без включения записи. Как у
fuel-history, `--mil-record-dir` автоматически задаёт и каталог истории.
При обоих флагах пути должны совпасть; MIL и fuel-каталоги остаются раздельными.
Только чтение истории не включает MIL polling и не создаёт writer/lock/каталог.
Каталог задаётся при запуске приложения, никогда через URL.

Новые GET endpoints:

- `/api/mil/history/sessions`: лёгкий каталог из проверенного manifest,
  source, retention и список сеансов/частей с состоянием файлов. Без полного
  анализа JSONL. Добавить read-only `milstore.List` с существующей валидацией.
- `/api/mil/history/report?session=<id>[&incident=<id>]`: отчёт существующего
  `milanalysis.Analyze`. Выбор session обязателен для HTTP, чтобы не анализировать
  весь архив на каждое открытие. Фильтр incident сохраняет оговорённую M3.3.5
  семантику: отфильтрованы окна, история/ответы сеанса остаются доступны.
- `/api/mil/history/incident?session=<id>&incident=<id>`: скачивание JSON
  выбранного сохранённого окна. Используется `milstore.Read`; содержатся только
  валидные строки с точной парой session/incident плюс границы сеанса и issues.
  Формат экспорта: version1, scope=incident_export, source/session/incident,
  filtered=true, rows (исходный envelope плюс file/line), issues, incomplete.
  Это проверенная выборка, не побайтовая копия и не полный управляемый архив.

История запрашивается при открытии страницы один раз: каталог и последний
доступный сеанс. Затем — при выборе/кнопке обновления, без таймера сканирования
архива на каждом SSE. Новое событие может показать подсказку обновить историю;
само наличие SSE не запускает анализ автоматически.

Для тяжёлых report/export — один одновременный запрос на Server, без очереди;
второй получает 429. Нет блокировки telemetry/fuel при чтении или анализе.
Контекст запроса ограничен 8 сек, клиентское ожидание — 10 сек. Списки,
сигналы отмены и ограничения reader сохраняются. JSON report/export ограничен
8 MiB; превышение даёт явную ошибку, не частичный «полный» снимок.

Разрешены только известные query-поля по одному значению, длина query <=2048,
валидные существующие идентификаторы; никакого имени файла или пути в query.
Ответы JSON `no-store`, прежние CSP/no-sniff/referrer headers сохраняются.
Восстанавливаемые проблемы reader (плохая строка, неполная часть, retention)
дают HTTP 200 с `incomplete=true` и issues: оставшиеся валидные доказательства
должны быть доступны. Это решение исполнителя повторяет контракт M3.3.5.
Ошибки: 400 неверный запрос, 503 история не настроена, 409 ошибка manifest/
открытия при повреждении/ротации/недоступности или отсутствующий выбранный объект,
429 занятый анализ,
504 истёкший timeout. В HTTP не раскрывается абсолютный путь или сырая ошибка
файловой системы. UI показывает понятную причину и возможность обновить список.

## Полнота, контекст и безопасность отображения

Активная часть/открытый incident, ранний старт/выход, ошибки записи, retention
и усечение сохраняют неполноту. Ошибка/исчезновение части во время ротации
предлагает повторить запрос; повреждённая история не превращается в отсутствие
ошибок двигателя. Неизвестные форматы/версии не интерпретируются автоматически.

Экспорт окна не привязывает к событию поздние ответы без incident; они доступны
в отчёте сеанса с отдельной подписью. Freeze frame отделён от live-значений.
Для каждого события видны retained/had_gaps, число кадров и ограничения;
из raw-ответов не восстанавливается время возникновения неисправности.

Находки показывают symptom/confidence, число и границы наблюдений, исходные
file/line/sequence, supporting/contradicting/missing/next_check. `observed`
переводится как наблюдаемый факт, `limited_hypothesis` — как гипотеза для
проверки. `insufficient_data` видно отдельно. Отсутствие находок не объявляется
исправностью; редкие O2 не дают заключения о катализаторе. CPU/BLE/ЭБУ не
выбираются причиной задержек автоматически.

Все сохранённые строки выводятся через `textContent`/DOM, не через HTML.
Ошибки/конкурирующие fetch не оставляют скачивание или заголовок от прежнего
выбранного сеанса; отменённый ответ не перезаписывает новый выбор.
Никаких POST/ECU-команд, очистки/удаления/редактирования файлов на этой странице.

history, повреждение/ротация, active/retention, лимиты/timeout/cancel/concurrency,
неизменность исходников, источник SIM против архива LIVE, две браузерные
подписки без второго source/ELM-сеанса. Предыдущие fuel/server/SSE тесты проходят.

Node tests: ON/OFF/UNKNOWN, пустые и недоступные DTC, invalid payload,
истечение MIL и источника по монотонным часам без новых SSE, future timestamps,
SIM, различие live/history, статусы полноты, независимые поздние ответы,
недостаточная частота O2 и безопасная обработка сохранённых строк.

Synthetic HTTP/browser smoke: SIM dashboard с временным MIL-архивом; страница,
навигация, выбор истории, JSON и снимок, disconnect/empty/error состояния.
Визуально проверить 1280×800 и узкий viewport доступным браузерным инструментом;
если его нет, документировать ограничение, а не заявлять визуальную приёмку.
