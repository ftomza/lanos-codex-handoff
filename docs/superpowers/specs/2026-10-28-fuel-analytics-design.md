# M6.1 — История, диагностика топлива и аналитика поездки

Дата: 2026-10-28. База: main `7cc6aa8`, ветка `feat/fuel-analytics`.
Статус: проект для одобрения владельцем, реализация ещё не начата.
Работа в текущей рабочей папке, без дополнительного worktree.

## Исходные данные и границы

Требования — M6.1 в PLAN.md, сохранённые в main коммитом `1471a63`.
Исправление ожидания ЭБУ уже включено в main. Сохранить его поведение.
Владелец сообщил итоги: 9.569 км, оценка 0.9369 л, 9.79 л/100 км,
98.4% покрытия наблюдаемого времени, speed_density, factor=1, incomplete.
Это не независимое измерение расхода. Файл итогов не содержит временного ряда:
восстановить из него графики и найти момент аномалии IAT невозможно.

В текущем Stream уже есть опрос throttle, STFT/LTFT и O2; LIVE Source
передаёт только часть этих ответов. Открыть для диагностики уже получаемые
параметры, сохранив расписание, capability gating и список ECU-команд.
Показать недоступность параметров, которые не приходят или успели устареть.
Не допрашивать новые PID ради полноты отчёта. Не использовать второй OBD-клиент.

Go 1.27, зависимости, формулы/пределы M6, модель VE и формат fuel state v1
остаются прежними. Новые поля API добавляются без изменения существующих.
В этом этапе нет измерения бака, подстановки IAT, автоматической коррекции
по STFT/O2 или доказательства точности модели. К автомобилю не подключаться.

## Варианты

1. **Рекомендуется:** встроенная запись согласованных исходных сигналов и
   результата одного Fuel Computer; общий потоковый анализатор используется
   CLI и экраном истории. Сохраняются реальные настройки и события управления.
2. Внешний recorder, читающий HTTP/SSE приборки. Разделяет процессы, но требует
   отдельного запуска и добавляет сетевые пропуски/рассогласование параметров
   и результата. Для сохранения сбросов/калибровки понадобится дополнительный
   событийный API. Не даёт преимуществ для текущей локальной приборки.

## Диагностический режим и совместимость

Запись выключена по умолчанию. `--fuel-record-dir=PATH` включает запись и
использует каталог также для чтения истории. `--fuel-history-dir=PATH` открывает
уже записанную историю; если указаны оба флага, пути должны совпадать.
Отдельные каталоги SIM/LIVE; смешивать их одним writer нельзя.
`--fuel-record-interval=1s` по умолчанию, допустимо 250ms..2s, чтобы интервал
оставался внутри существующего максимума интегрирования 3s.
Запись требует включённого топливного модуля. Просмотр разрешён с `--fuel=off`.
Все флаги валидируются до открытия адаптера. Обычный запуск M6 не меняется.

Сервер получает согласованную неизменяемую запись из того же Computer,
который ведёт учёт: исходные сигналы, результат, промежуточные вычисления,
накопленные исходные/скорректированные итоги и состояние калибровки относятся
к одной версии наблюдения. Чтение HTTP/истории не вызывает интегрирование.
Хранить только ограниченную очередь (256 записей), не блокировать ECU на I/O.
При переполнении остановить запись с видимой ошибкой и признаком неполноты,
продолжив основные приборы и учёт M6. Не терять точки молча.

Записывать версионированный JSONL v1: session_start, sample, event, session_end.
Каждая строка содержит session_id, sequence, UTC-время и elapsed_ns процесса;
для sample — generation, источник, health и настройки модели.
После перезапуска начинается новая session; предыдущая история сохраняется.
Новый файл не дописывается к аварийно оборванной сессии.

Sample содержит:

- RPM, скорость, MAP, IAT, ОЖ, дроссель, доступные trims и O2, MAF/direct flow.
  У каждого: PID/происхождение, единицы, support/status, исходные capture/receipt
  timestamps, возраст, TTL и признак применимости. Повтор snapshot не является
  новым измерением IAT. O2 обозначать номером сенсора/PID; не угадывать банк.
- Значения расчёта л/ч, л/100 км, среднее с момента сброса; причину
  недоступности, модель, provenance/confidence и качество входов.
- Для speed-density: MAP в Pa, IAT в K, rho в kg/m³, объёмный поток m³/s,
  воздух g/s, VE, AFR, плотность g/L, расход до/после поправки. Это результаты
  того же вычисления, не отдельная формула в recorder. При RPM=0 сохранять
  причину нулевого расхода; отсутствующие промежуточные входы остаются null.
- Исходные и скорректированные накопленные литры/км, jointly covered totals,
  observed/covered/gap time, reset_at, revision, factor, fingerprint модели.

События: начало/конец процесса, reconnect/generation, потеря доступности,
успешный сброс/калибровка и ошибка записи. Сброс не удаляет историю, калибровка
не переписывает старые строки. Не включать VIN или сырые ответы с идентификаторами.

## Ограничения, долговечность и восстановление

По умолчанию 16 MiB на файл, восемь файлов суммарно, включая активный.
Флаги: `--fuel-record-max-bytes` (1..64 MiB), `--fuel-record-max-files` (1..32).
Строка ограничена 64 KiB. Перед превышением лимита закрыть часть и открыть
следующую; удалить только самый старый закрытый файл, принадлежащий manifest.
Посторонние файлы не удалять. При удалении начала записи отчёт и UI показывают
retention_truncated; полный интервал больше не считается сохранённым.

Каталог 0700, файлы 0600, один writer с отдельным sidecar lock. Минимальный
версионированный manifest атомарно хранит порядок частей и принадлежность
источнику; его размер ограничен числом файлов. fsync не реже раза в 5s,
при ротации и нормальном завершении. При аварии возможна потеря последних 5s.
Не удалять чужой/неизвестный lock и не обнулять повреждённый manifest.
Ошибка первоначального открытия записи останавливает запуск до Source.Start;
runtime-ошибка записи видна в API/UI, основные приборы продолжают работать.

После аварии reader принимает завершённые корректные строки, помечает
незавершённый хвост и отсутствие session_end как неполноту. Некорректная
внутренняя строка, неизвестная версия и пропуск sequence явно диагностируются;
не соединять данные по разные стороны повреждения. Никакого молчаливого ремонта.
Прошлые файлы читать потоково, не загружать всю историю в память.

## Анализ и воспроизведение offline

Новый CLI `fuelanalyze --input=DIR --json` читает ту же схему и не открывает
адаптер/топливное состояние. Текстовый вывод по умолчанию, JSON для экспорта.
Один анализатор обслуживает также HTTP. Отчёт содержит настройки, причины
неполноты, сохранённый диапазон, сессии и источники каждого результата.

Расчёты выполняются только для валидных соседних точек одной session/generation
и модели, с dt>0, dt<=3s и свежими входами. Разорвать интервал при пропуске
sequence, reset, калибровке, обратном времени и повреждении файла.
Один новый процесс не продолжает elapsed_ns предыдущего. Реальный промежуток
между процессами неизвестен для учёта; UTC показывает границы, но не создаёт
литры/пробег. Покрытие относится к наблюдаемому сохранённому диапазону.

Общие расход/пробег брать из валидных разностей сохранённых исходных счётчиков
с учётом событий и factor; не трактовать скачок калибровки как израсходованное
топливо. Сравнивать с интегрированием валидных точек как диагностикой, явно
обозначив дискретность выбранного интервала записи. Несовпадение не скрывать.
Не смешивать накопленный итог со сброса и расход только внутри выбранной записи.

Отчёт: наблюдаемая длительность/пробег, средняя скорость как км/валидные часы,
максимальная наблюдавшаяся скорость; движение при свежей speed>0, холостой ход
при speed=0 и RPM>0, остановленный двигатель при обоих нулях, иначе unknown.
Для каждого режима — валидное время, покрытие, литры и л/ч; л/100 км только
при достаточном jointly covered distance. Не считать неизвестную скорость idle.

Сегменты делятся при restart/generation/reset/model/factor и дополнительно
по минутам. Средний расход — 100*joint_liters/joint_km, не среднее отношений.
Распределения: RPM 0/1–999/1000–1999/2000–2999/3000+; скорость
0/(0,5)/[5,30)/[30,60)/60+; MAP (0,30)/[30,60)/[60,90)/90+ kPa.
Показывать время/литры и отдельный unknown. Интервалы, пересекающие границу
диапазона без достаточных наблюдений, маркировать mixed вместо выдуманного
точного разбиения. Все границы и единицы включить в отчёт.

## IAT и качество входов

Проверки являются эвристиками для расследования, не диагнозом датчика:

- Вне текущей области модели (IAT<=−30°C или >100°C) — недоступный вход.
  −40°C сохраняется как наблюдение/аномалия, не заменяется на +20°C.
- Постоянное значение: разброс <=0.5°C не менее 5min при RPM>0 и не менее
  десяти различных свежих измерений IAT, без разрыва. Дубликаты не учитываются.
- Скачок >=15°C между отдельными измерениями за <=10s — предупреждение,
  включая переход −40→20. За пропуском сравнение не продолжается.
- Для холодного старта требуется явная отметка владельца
  `--fuel-record-cold-start`. Тогда в первые 30s свежих данных сравнить IAT и
  ОЖ с разницей capture time <=5s; |delta|>15°C — диагностический признак.
  Без отметки проверка имеет статус not_evaluated; холодный запуск не угадывать.

Качество: UNAVAILABLE, если сам расчёт недоступен; DEGRADED — расчёт существует,
но есть IAT-предупреждения/неподтверждённые предпосылки; VALID — входные проверки
пройдены. Это не вероятность и не процент точности расхода. LIVE speed-density
с непроверенным IAT/постоянным непроверенным VE остаётся DEGRADED.
Покрытие, калибровка, модель и confidence показываются отдельно.
Опциональные `fuel.quality`/diagnostics дополняют API; старые status/reason
и запрет live unverified IAT без явного opt-in сохраняются.

## Экран «Аналитика поездки»

Отдельная страница в текущем Go dashboard, в существующем оформлении и без
новых JS-зависимостей. Выбор сохранённой сессии/диапазона, отчёт и Canvas-графики
RPM/скорости/MAP/расхода, накопленных литров и среднего с момента сброса.
Явные source=LIVE/SIM, метка «История», настройки/factor и качество модели.
Состояние сегодняшнего live snapshot не подставляется вместо истории.

Пропуски разрывают линии; предупреждения/сбросы/калибровка отмечены на оси.
Для экрана ограничить выдачу 4000 точками на ряд, сохраняя разрывы и экстремумы
по временным корзинам; обозначить прореживание. Анализ агрегатов использует
все валидные строки независимо от графического прореживания.
Reader/API имеют пределы диапазона, размера строки и количества файлов.
HTTP принимает только идентификаторы из настроенного history-каталога,
не произвольные пути; выгрузка не изменяет файлы. Нет удалённого управления ECU.

Offline-просмотр: `dashboard --source=sim --fuel=off --fuel-history-dir=PATH`,
затем открыть страницу аналитики; Bluetooth при этом не запускается.
Счётчики основного M6 и диагностика хранятся раздельно. История доступна после
перезапуска даже при выключенной записи, в пределах объявленной ротации.
