# Топливный компьютер M6

Реализован в `feat/fuel-computer`, проверен offline. Точность реального расхода
на Lanos пока не проверена. Это оценка топлива за записанные интервалы, не
датчик уровня бака и не запас хода. ЭБУ остаётся read-only.

## Запуск

```sh
make build-dashboard
./bin/dashboard --source=sim
```

Открыть http://127.0.0.1:8080. По умолчанию топливный модуль включён; отключить
его можно `--fuel=off`. При обычном запуске Bluetooth не открывается.
В новом блоке показаны мгновенный расход, средний по совместно учтённым
интервалам, литры и пробег после сброса, модель, покрытие и состояние сохранения.
При скорости от 5 км/ч мгновенный расход — л/100 км, ниже — л/ч. Если скорость
неизвестна, показывается л/ч с соответствующей подписью, без утверждения о холостом
ходе. Порог задаёт `--fuel-low-speed` (1..30 км/ч).

## LIVE нашего Lanos

Сначала подтвердить текущее состояние припаркованного автомобиля и следовать
[NEXT_CONNECTION.md](NEXT_CONNECTION.md). Не запускать грабер/другой OBD-клиент
одновременно. Новая приборка и топливный модуль физически ещё не проверялись.

Обычный LIVE-запуск сохраняет основные приборы, но расход при работающем двигателе
будет недоступен с причиной `unverified_iat`. Для сознательной экспериментальной
оценки по фактическому IAT:

```sh
./bin/dashboard --source=elm327 --transport=ble --ble-name=IOS-Vlink \
  --retries=0 --fuel-allow-unverified-iat \
  --fuel-state=data/fuel/live-experimental.json
```

Отдельный файл не смешивает эту поездку с ранее созданной конфигурацией LIVE.
В API/UI остаётся предупреждение «IAT не проверен», confidence=low. Флаг не
подставляет +20°C: используются только свежие ответы ECU. IAT <=−30°C и >100°C,
MAP вне (0,120] kPa, RPM вне [0,7000] и нечисловые значения модель не принимает.
Это границы применимости модели, не диагноз датчика. Записанные −40°C не
превращаются в расход. Постоянные +20°C остаются непроверенным входом.
Свежий RPM=0 позволяет модели установить нулевой расход остановленного двигателя;
отсутствующий/устаревший RPM не становится нулём.

## Методы и допущения

`--fuel-model=auto` выбирает метод по заявленным возможностям источника:

1. `direct`: объявленный PID 5E, расход ЭБУ в л/ч; его точность тоже не доказана.
2. `maf`: объявленный PID 10, оценка из g/s воздуха с номинальной смесью/плотностью.
3. `speed_density`: оценка из RPM, абсолютного MAP и IAT.

Принудительно выбрать метод можно `--fuel-model=direct|maf|speed_density`;
это не разрешает опрос неподдержанных PID. На наблюдавшемся Lanos MAF и PID 5E
отсутствуют, поэтому они не запрашиваются. MAP/IAT уже входят в общий live stream.
Метод фиксируется в пределах поколения соединения. Временная недоступность
выбранного входа не переключает формулу незаметно. При смене модели учёт топлива
приостанавливается до явного нового отсчёта; основные приборы продолжают работать.

Настройки по умолчанию — **допущения**, не результат калибровки машины:

| Параметр | Флаг | Значение |
| --- | --- | --- |
| Объём четырёхтактного двигателя | `--fuel-displacement` | 1.5 л |
| Постоянный коэффициент наполнения | `--fuel-ve` | 0.75 |
| Массовое отношение воздух/бензин | `--fuel-afr` | 14.7 |
| Плотность бензина | `--fuel-density` | 745 г/л |

АИ-92 не устанавливает точную плотность, состав или AFR. Полезная карта VE,
обогащение и отсечка топлива на торможении двигателем неизвестны. Коррекции/O2
автоматически не умножаются на расход, DFCO не угадывается по дросселю/RPM.
После скалярной поправки модель всё равно остаётся приблизительной.
Пределы расхода/MAF: 100 л/ч и 200 г/с; выход за пределы — недоступно, не clamp.

Формула speed-density, с явными единицами:

```
T = IAT_C + 273.15
rho_kg_m3 = MAP_kPa * 1000 / (287.05 * T)
volume_m3_s = displacement_L / 1000 * RPM / 120 * VE
air_g_s = rho_kg_m3 * volume_m3_s * 1000
fuel_L_h = air_g_s * 3600 / (AFR * density_g_L)
```

Инжекторная модель отсутствует: нет подтверждённой длительности импульса и
характеристик форсунок. Тестовые синтетические входы не являются фактами об ECU.

## Учёт и пропуски

Один backend-компьютер обслуживает все браузеры. Тик 250ms и обновления источника
используют монотонное время процесса; повторная временная отметка не добавляет
литры второй раз. Валидные интервалы интегрируются трапециями. Интервалы >3s,
истёкшие входы, обратное время, смена поколения, обрыв и отсутствующие значения
не соединяются расчётом. Данные не продолжаются за срок их свежести.

Отдельно считаются весь записанный пробег, литры при валидном расходе и совместно
учтённые литры/километры. Средний = 100 * совместные литры / совместные км,
начиная с 0.1 км. Пробег без расхода не разбавляет среднее. Поэтому литры/общий
пробег могут не давать показанное среднее при неполном покрытии — подпись об этом
остаётся видимой. Время покрытия относится только к наблюдаемому процессом
интервалу, не гарантирует полноту всей поездки.

Мгновенный расход скрывается при потере связи/истечении входов и в браузерном
watchdog. Исторические итоги остаются с датой сброса в API и отметкой частичного
покрытия. Никаких литров/километров за неизвестный промежуток между процессами
не добавляется. После перезапуска сохраняются итоги и ставится `process_restart`;
двигатель сам по себе не сбрасывает поездку. Для нового полного интервала нужно
явно нажать «Сброс» после установки связи.

## Сохранение, сброс, ошибки

Файлы по умолчанию относительно текущего каталога запуска:
`data/fuel/sim.json` и `data/fuel/live.json`. Путь меняет `--fuel-state`.
Каталог data/fuel игнорируется Git; новый каталог создаётся 0700, файл 0600.
Версионированный JSON хранит исходные итоги, покрытие, конфигурационный fingerprint,
коэффициент, reset/save timestamps и revision. Мгновенные значения и временная
опора не сохраняются. Сохранение: временный файл + fsync + atomic rename, раз в
5s, при локальном изменении и нормальном завершении. При аварийном завершении
процесса возможна потеря последних 5s; это не гарантия сохранения при обесточивании.

Sidecar `.lock` запрещает два писателя. Не удалять lock живого процесса. После
аварии сначала убедиться, что прежний dashboard/helper завершён, сохранить копию
state и только затем вручную убрать оставшийся lock. Неизвестный lock программа
не удаляет. Повреждённое состояние не заменяется нулевой поездкой. Ошибка файла,
версии или конфигурации останавливает запуск до открытия адаптера.

Изменение модельных настроек требует отдельного файла или явного
`--fuel-reset-state`: новый отсчёт и коэффициент 1. Не оставлять этот флаг в
обычной команде — он означает новый отсчёт при каждом запуске. Некорректный JSON
сначала сохранить/исследовать: этот флаг не подавляет повреждение файла.

«Сброс» в UI обнуляет итоги/покрытие только после подтверждения. Коэффициент
сохраняется, если не отмечено возвращение к 1. Ошибка сохранения не подтверждает
сброс/калибровку. Runtime-ошибка видна в UI/API как `persistence_error`; актуальные
непроверенные на диске итоги не выдаются за сохранённые. CLI возвращает реальную
ошибку при завершении. Завершать Ctrl+C, не kill -9.

## Калибровка

Нужны независимо измеренные литры от полного бака до полного и **точно тот же**
интервал после сброса. Минимум 10 совместно учтённых км, без пропусков и смены
модели. Прерванную запись нельзя исправить множителем. Старый отчёт 167→177 км
не содержит нужных измеренных литров.

В UI: «Калибровка» → литры и подтверждение совпадающих full-to-full границ →
«Рассчитать поправку» → проверить старый/новый коэффициент → «Применить».
Фактор = measured_liters / base_liters, допустимо 0.25..4. Предпросмотр получает
токен: применяется показанный коэффициент, даже если между просмотром и нажатием
пришли новые измерения. Другая калибровка/сброс/предпросмотр может сделать токен
неактуальным. При появлении пропуска применять его нельзя.

Исходные итоги неизменны, коэффициент масштабирует текущие/исторические литры.
Можно отменить последнюю поправку или вернуть ×1. Поправка не превращает
приблизительную VE/смесь в измеренный расход и не подтверждает точность IAT.

## API

`GET /api/snapshot` и SSE содержат optional `fuel`: instantaneous flow/ratio,
метод/provenance/confidence/reason, отдельные `flow_until`/`speed_until`, итоги,
покрытие/reasons, factor/settings, revision и persistence. `generation` в исходной
телеметрии разрывает интеграцию даже при пропуске промежуточного gap-сообщения.

Только локальные JSON POST, не команды ECU:

- `/api/fuel/reset`: `expected_revision`, optional `default_factor`.
- `/api/fuel/calibration/preview`: `expected_revision`, `measured_liters`, `full_to_full`.
- `/api/fuel/calibration`: `action=apply|undo|default`, `expected_revision`; для
  apply также те же литры/подтверждение и `preview_token` из предпросмотра.

Обязательны совпадающий Origin, application/json, тело ≤4KiB, корректные поля и
revision. Cross-origin=403, неподходящий тип=415, устаревшая revision=409,
недопустимая калибровка/JSON=400, сохранение=500, модуль выключен=503.
Сеть по-прежнему доверенная локальная, без аутентификации/TLS.

## Проверка

Unit/integration: формулы/единицы, нули/пропуски/границы/устаревание, поколение,
запрет выдуманной отсечки, временные интервалы/повторные отметки, общий учёт,
сохранение/порча/lock/перезапуск, обратимые поправки и сброс, origin/JSON/revision.
Собранный симулятор проверен через HTTP, два SSE-клиента, сохранение, сброс,
перезапуск и SIGINT с активными потоками. Визуальная проверка нового блока в
настоящем браузере и на Teclast ещё не выполнена; нужны 1280×800 и узкий экран.
Ни эти тесты, ни старые поездки не подтверждают точность M6 на автомобиле.
